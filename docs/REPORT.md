# Отчёт о проверке очереди

## Решение о выпуске при 100 запросах/с

**DON’T SHIP в штатной конфигурации из четырёх worker.** В отдельном замере API принял 2 000 новых заданий за 19,994 с. Все ответы были `201`, p99 HTTP составил 6,64 мс. При первом замере после окончания подачи 992 задания ещё ждали и 4 выполнялись. Очередь полностью опустела через 20,8 с после окончания входящего трафика. Для этого профиля стенд обрабатывал около 50 заданий/с. Постоянный поток в 100 новых заданий/с будет увеличивать время ожидания даже при быстрых ответах API. Все 1 913 успешных заданий дали по одному эффекту. Остальные 87 завершились запланированной ошибкой. [Сырой вывод замера](evidence/20261109T202134Z-capacity-seed8101-bxxetyuemu.log)

**Первое исправление** — подобрать число worker по реальной длительности обучения и допустимому времени ожидания. На этой смеси длительностей среднее требование к вычислению около 77 мс на задание. При 100 новых заданиях/с это примерно 7,7 одновременно занятых worker ещё до учёта SQL и отказов. Для выбора рабочего числа реплик нужно повторить замер с запасом, отслеживая возраст старейшего задания и p99 от приёма до завершения. Если вход может превышать мощность, потребуется ограничение приёма новых заданий с сохранением возможности получить результат по уже принятому ключу.

## Что проверял chaos-тест

Один прогон создаёт свежую БД и 8 отдельных worker-контейнеров. На 10 000 ключей приходится 15 334 HTTP-запроса под нагрузкой — 10 000 созданий, 3 334 повтора и 2 000 отмен. Две копии POST с одним ключом могут прийти в любом порядке. Отмена отправляется сразу после ответа на создание, пока для других ключей продолжается подача. Каждые две секунды Docker посылает выбранному процессу SIGKILL. Генератор проверяет код выхода 137 и перезапускает контейнер. Номер попытки в БД позволяет увидеть реальные повторные захваты.

Для каждого ключа генератор сохраняет исходные параметры, выданный ID и ответ на отмену. После подачи он ждёт завершения очереди с ограничением времени. Затем сверяет множества принятых и сохранённых ключей, ID, параметры, терминальные состояния, очищенные lease, число строк эффекта и номер записавшей попытки. Поэтому потерю одного задания обнаружит проверка его ключа, даже если дубликат другого сохранил общее число строк. Генератор также читает все страницы HTTP API и запрашивает статус каждого 101-го задания. Эти чтения выполняются после нагрузочного окна. [Код сверки](cmd/chaos/verify.go)

### Журнал прогонов

- **4101, исследовательский прогон.** 76 убийств, 26 заданий захвачены повторно, p99 HTTP 5,95 мс. Инварианты выполнены. [Полный вывод](evidence/20261109T201011Z-seed4101-c0a14b01d6.log)
- **4102, исследовательский прогон.** 76 убийств, 31 задание захвачено повторно, p99 HTTP 11,22 мс. Инварианты выполнены. Эти два запуска использовали первоначальный генератор на Python. Его версия сохранена в истории Git в коммите `2f6dcfb`. [Полный вывод](evidence/20261109T201321Z-seed4102-0ab80a701c.log)
- **7401, итоговый генератор на Go.** 76 убийств, 29 заданий захвачены повторно, p99 HTTP 7,49 мс. С учётом ожидания от планового времени отправки p99 составил 9,75 мс. Инварианты выполнены. [Полный вывод](evidence/20261109T201839Z-chaos-seed7401-f2ku4fgxmx.log)
- **7402, итоговый генератор на Go.** 76 убийств, 41 задание захвачено повторно, p99 HTTP 5,33 мс и p99 от планового времени 8,06 мс. Инварианты выполнены. [Полный вывод](evidence/20261109T202236Z-chaos-seed7402-jhzhm64bfe.log)

**Итого — 4 полных chaos-прогона, 40 000 заданий, 304 SIGKILL и 127 заданий с повторным захватом.** В каждом прогоне получилось 7 652 succeeded с 7 652 эффектами, 348 ожидаемых failed и 2 000 cancelled без эффектов. При сверке каждого ключа обнаружено 0 потерь, 0 повторных эффектов и 0 зависших running. Все отмены в нагрузочном профиле успели победить, поэтому противоположный исход проверялся отдельно в тесте гонки. Один дополнительный контрольный нагрузочный прогон на четырёх worker описан в начале отчёта.

Фиксированный seed позволяет воспроизвести состав нагрузки. Число захватов и задержки могут меняться. Все журналы содержат вывод отдельного запуска, включая отрицательный эксперимент ниже. SQL и HTTP проверяются с разных сторон границы сервиса. Целевой эффект находится в той же PostgreSQL-транзакции, что и смена состояния на succeeded.

## Тихие отказы

1. **Двойной захват.** Тест удерживает блокировку на первом задании и одновременно выпускает восемь претендентов на второе. Победитель один, его номер попытки равен 1. После освобождения блокировки первое задание также доступно. В отдельном тесте два worker обрабатывают задание длительностью 2,6 с при lease 1,5 с. Оно завершается с первой попытки благодаря продлениям. [Тесты протокола](internal/queue/protocol_test.go) · [PostgreSQL о SKIP LOCKED](https://www.postgresql.org/docs/17/sql-select.html#SQL-FOR-UPDATE-SHARE)
2. **Возврат просроченного worker.** Проверены два момента — сразу после истечения lease и после выдачи новой попытки. В обоих случаях старый worker теряет право на продление и запись. Есть отдельное воспроизведение, в котором завершение встаёт на блокировку до дедлайна, а получает строку после. Тест подтверждает ожидание через `pg_blocking_pids`. Порядок «сначала взять блокировку, затем проверить время» закрывает это окно. Владелец, уже прошедший проверку под блокировкой, удерживает её до фиксации или отката.
3. **Отмена одновременно с завершением.** Проверены оба последовательных порядка и 46 конкурентных стартов. В штатном запуске выиграли 30 отмен и 18 завершений. Ответ отмены совпал с конечным состоянием в БД. Во всех случаях succeeded имел один эффект, cancelled — ноль. [Сырой вывод](evidence/protocol-01.log)
4. **Повтор запроса и изоляция.** Первый INSERT оставлен незафиксированным, второй запрос с тем же ключом наблюдаемо заблокирован. После COMMIT первый ID возвращается повторному клиенту. Тест читает фактический уровень изоляции. При READ COMMITTED второй SQL-оператор получает свежий снимок и видит победителя конфликта. Проверены также повтор после отмены и ответ 409 при изменённом содержимом. [HTTP-тест](internal/queue/http_test.go) · [PostgreSQL о READ COMMITTED](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED)
5. **Расхождение часов.** Go-тест через `testing/synctest` запускает код клиента БД с локальным временем в 2000-м и затем в 2059-м годах. PostgreSQL продолжает работать с датой 2026 года. В обоих случаях проверены захват, продление, оставшийся по часам БД срок и завершение. Скачок часов самого primary остаётся отдельным риском. [Наблюдавшиеся даты](evidence/protocol-01.log) · [PostgreSQL о clock_timestamp()](https://www.postgresql.org/docs/17/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT)
6. **Ошибка между сменой состояния и записью эффекта.** В тестовой схеме временное ограничение отвергает INSERT в effects. После ошибки задание всё ещё running, таблица эффектов пуста. После снятия ограничения та же попытка фиксирует состояние и один эффект. Отдельная проверка остановила и вновь запустила Compose с тем же томом. Статус, ID, ответ на повторный POST и единственная строка эффекта сохранились. [Лог перезапуска](evidence/restart-01.log)

### Отрицательный контроль

В отдельный тестовый контейнер была смонтирована копия `store.go`, в которой из предиката владения удалено только `AND lease_until > clock_timestamp()`. Проверки состояния и номера попытки оставались. Два теста упали с кодом выхода 1. Первый поймал принятие результата просроченной попытки до следующего захвата. Второй поймал запись после ожидания блокировки. В поставляемой версии предикат присутствует. Все 9 интеграционных тестов прошли в Compose и ещё раз с `go test -race` на отдельном PostgreSQL. Команда `go vet ./...` завершилась успешно. [Необработанный вывод сбоя](evidence/mutation-01.log) · [Штатный прогон](evidence/protocol-01.log) · [Прогон с детектором гонок](evidence/race-01.log)

## Границы вывода

Убийства затрагивали worker. Не испытывались аварийное переключение PostgreSQL, потеря диска, сетевое разделение и длительная эксплуатация с растущими таблицами. При мгновенном перезапуске контейнера короткий сбой не всегда попадает в выполняющееся задание. Лог выделяет число заданий с повторным захватом. Генератор проверяет итоговые записи в БД, но реальный внешний запуск обучения, расход GPU или отправка уведомления потребуют своего идемпотентного протокола. Отменённое задание может продолжать локальное вычисление до следующей проверки, даже когда запись результата уже запрещена.

**Что удивило и что беспокоит.** При одинаковых 100 HTTP-запросах/с интерфейс оставался быстрым как в смешанном сценарии, так и в сценарии из одних созданий. Но во втором случае к последнему ответу API почти половина заданий всё ещё ждала. Для реального обучения больше всего беспокоит время между подтверждением `201` и получением результата при длинных заданиях. Короткие имитации на одном хосте дают только начальную оценку этой задержки.

## Использование ИИ и личная проверка

Codex прочитал проектную записку до кода, реализовал тесты и генератор, выполнил команды Docker/Go и составил этот отчёт по журналам. В решение также вошли предложенные ИИ захват через SKIP LOCKED. Для проверки этих решений Codex воспроизвёл реальное ожидание блокировки, сдвинул часы тестового клиента, спровоцировал ошибку INSERT и запустил мутант без проверки срока lease. Первоначальный генератор эксперимента был переписан на Go, чтобы поставляемые сервис и инструменты запускались на одном языке.
Мною написана основная структура кода, номер попытки как щазита от старого владельца и транзакционная запись эффекта, а также сборка проекта на Docker. Весь код агента был проверен мной и другим агентом validate.

Для собственной проверки можно создать задание с одним ключом дважды, отменить его, прочитать итог через API, затем сверить число эффектов в PostgreSQL. Команды запуска и повторения экспериментов приведены в [README](README.md).
