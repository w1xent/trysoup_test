# Исправления после security-review

## Доступ к API

Все операции с заданиями требуют заголовок `Authorization: Bearer <token>`. Токен связан с владельцем из конфигурации сервера. Клиент получает список, статус и возможность отмены только своих заданий. Чужой ID возвращает 404. Ключ идемпотентности уникален в пределах владельца, поэтому одинаковые ключи разных клиентов создают разные задания.

При первом запуске Compose создаёт владельца `operator` со случайным токеном. В режиме прямого запуска задайте `API_TOKENS_FILE` — путь к JSON-файлу вида `{"alice":"<случайный-токен-длиной-минимум-32-байта>"}`. Без корректной конфигурации токенов API завершает запуск с ошибкой. Health-check доступен без токена.

POST требует `Content-Type: application/json`. Защита `http.CrossOriginProtection` отклоняет межсайтовые изменяющие запросы, включая отмену с переданным токеном. Проверены также обычная HTML-форма и отсутствие авторизации. [Реализация](../internal/httpapi/auth.go) · [Проверки](../internal/queue/security_test.go)

Прямой запуск слушает `127.0.0.1:8080` по умолчанию. В контейнере адрес явно задаётся через `HTTP_ADDR`, а наружу Compose публикует только loopback. Для доступа по внешней сети Bearer-токен нужно передавать через HTTPS.

## Ограничения очереди

Для одного владельца одновременно допускаются до 100 незавершённых заданий с суммарной заявленной длительностью до 120 000 мс. Общие пределы — 1 000 заданий и 600 000 мс. В сумме учитываются queued и running, поэтому запуск работы не освобождает квоту. Например, два минутных задания исчерпают бюджет одного владельца.

Проверка лимитов и INSERT выполняются под транзакционной advisory-блокировкой PostgreSQL. Это защищает от одновременного превышения квоты через несколько API-процессов. Новый запрос при заполнении возвращает 429 с `Retry-After: 1`. Повтор уже принятого ключа продолжает возвращать прежнее задание. Генератор повторяет отклонённые POST не более трёх минут и отражает все ответы в счётчиках. Скорость фактических запросов может отличаться от запланированной из-за повторов. [Приём заданий](../internal/queue/store.go)

## PostgreSQL

Сервис bootstrap генерирует случайные отдельные пароли для `queue_api`, `queue_worker` и `queue_admin`. Они хранятся в разных Docker-томах с ограничениями доступа к файлам. API получает только свой том и токены. Worker получает только свой том. Административные реквизиты доступны настройке БД и контейнеру тестов.

Прикладные роли не имеют SUPERUSER, CREATEDB, CREATEROLE, REPLICATION и BYPASSRLS. API читает и создаёт задания, меняет поля отмены. Worker читает задания, изменяет поля выполнения и вставляет эффекты. Схемой владеет административная роль. Unix-сокет с локальным доверенным входом смонтирован только в БД и сервис настройки. Клиентские сетевые соединения требуют TLS и SCRAM-пароль. [Настройка ролей](../scripts/db-setup.sh) · [Compose](../compose.yaml)

Клиент принимает только `sslmode=verify-full`. Собственный CA позволяет проверить сертификат и имя сервера `db`. Сертификат сервера выпускается на один год. При его истечении потребуется перевыпуск и перезапуск компонентов с согласованными сертификатами. Режимы без полной проверки отклоняются при открытии хранилища. [Генерация реквизитов](../internal/bootstrap/bootstrap.go) · [Режим verify-full](https://www.postgresql.org/docs/17/libpq-ssl.html)

Драйвер заменён с `lib/pq v1.10.9` на `pgx v5.12.0` с сохранением интерфейса database/sql. Проверка поддельного сервера с доверенным тестовым сертификатом отправляет нулевую длину сообщения во время Claim. Клиент возвращает ошибку `invalid message length`. Отдельный тест подтверждает отказ соединения с недоверенным сертификатом до отправки данных startup. [Тесты протокола](../internal/queue/transport_test.go) · [Версия pgx](https://github.com/jackc/pgx/releases/tag/v5.12.0)

## Обновление существующего тома

Команда `docker compose up --build` запускает настройку ролей и идемпотентное обновление схемы. Старые задания сохраняют ID, параметры и состояние и получают владельца `legacy`. Этот владелец зарезервирован и недоступен через API. Администратор может назначить выбранные старые задания известному владельцу через SQL, проверив совпадения ключей.

У старой роли `queue` отключаются вход и пароль. Если она имеет системный OID 10, PostgreSQL требует сохранить у неё SUPERUSER. Новые API и worker используют отдельные ограниченные роли. Миграция проверена на отдельном томе, созданном исходной версией Compose. Сохранность задания и отключение старого входа подтверждены. [Журнал миграции](../evidence/security/migration-02.log)

## Результаты проверок

Полный набор из 19 тестов прошёл с настоящим PostgreSQL под TLS, включая `go test -race`. Команда `go vet ./...` также завершилась успешно. На живом API проверены 401 без токена, 403 при межсайтовой отмене и 429 при превышении длительности. Системные представления подтвердили отсутствие административных прав у прикладных ролей и использование TLS всеми соединениями API и worker. [Прогон с детектором гонок](../evidence/security/race-01.log) · [Проверка API и ролей](../evidence/security/live-api-01.log)

В каталоге журналов сохранены промежуточные неудачи. Первый запуск использовал сертификат Ed25519, несовместимый с SCRAM channel binding на проверенном стенде. Он заменён на ECDSA P-256. Затем исправлена передача пробела в уровне изоляции новому драйверу. Тест со сдвигом часов перенесён на заранее установленное TLS-соединение, поскольку сертификат 2026 года ожидаемо отвергается при времени клиента 2000 года. Первая миграция откатилась при попытке снять SUPERUSER с обязательной bootstrap-роли. Первый chaos-прогон остановился на новом штатном ответе 429. Исходные журналы этих запусков сохранены. [Все журналы исправлений](../evidence/security/)

Итоговый полный chaos-прогон с seed 7411 принял и проверил 10 000 заданий после 75 SIGKILL. Получилось 7 691 succeeded, 351 failed и 1 958 cancelled. Зафиксировано 7 691 эффектов, 39 заданий захвачены повторно. Все ключи и состояния сверены, потерь, двойных эффектов и зависших running нет. В ходе подачи было 123 ответа 429, после которых генератор повторил запросы.
