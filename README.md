# Очередь заданий на обучение

HTTP-сервис на Go с PostgreSQL 17. Задание имитирует вычисление заданной длительности. При успехе worker записывает в `effects` идентификатор задания и номер попытки. По этой таблице можно посчитать фактические зафиксированные эффекты.

[Исправления security-review и миграция](docs/SECURITY.md) · [Журналы проверки исправлений](evidence/security/)

## Запуск

В корне репозитория выполните команду с Docker Compose v2.

```sh
docker compose up
```

Compose собирает Go-бинарник, поднимает PostgreSQL, один API на `127.0.0.1:8080` и четыре отдельных контейнера worker. Пароли, токен и сертификаты генерируются автоматически при первом запуске. Перед стартом API выполняется обновление схемы и настройка ролей БД. Команда `docker compose down` останавливает стенд с сохранением данных. Для другого порта задайте `HTTP_PORT`. Для восьми worker используйте `docker compose up --scale worker=8`.

## API

Пример создания задания.

```sh
TOKEN=$(docker compose exec -T api /queue token)
curl -i http://127.0.0.1:8080/jobs \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: experiment-17' \
  -d '{"name":"baseline","duration_ms":3000,"should_fail":false}'
```

При первой записи сервер возвращает `201 Created`, JSON с числовым `id` и заголовок `Location`. В пределах одного владельца тот же ключ и параметры возвращают `200 OK` с текущим состоянием задания. Тот же ключ с другими параметрами возвращает `409 Conflict`. Длительность допустима от 1 до 60 000 мс, ключ и имя занимают от 1 до 200 байт. `should_fail` по умолчанию равен `false`. Значение `true` имитирует ошибку обучения.

Для запросов статуса и отмены подставьте полученный идентификатор вместо `1`.

```sh
curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8080/jobs/1
curl -H "Authorization: Bearer $TOKEN" 'http://127.0.0.1:8080/jobs?limit=25&after=0'
curl -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" http://127.0.0.1:8080/jobs/1/cancel
curl http://127.0.0.1:8080/health
```

- При превышении лимита незавершённых заданий или их суммарной длительности новый POST возвращает 429. Детали лимитов приведены в security-документации.
- Статус содержит `id`, `key`, параметры задания, `state` и `attempt`. До первого захвата номер попытки равен нулю.
- Список возвращает `items` и `next_after`. Если курсор равен `null`, страниц больше нет. Размер страницы по умолчанию 50, максимум 100. Каждая страница видит зафиксированные к моменту запроса строки. При одновременных вставках задание с меньшим ID может зафиксироваться после выдачи курсора.
- Отмена возвращает `200` и состояние после разрешения гонки. Для `queued` или `running` это `cancelled`. Для уже завершившегося задания сервер возвращает его итог. Неизвестный ID даёт `404`, некорректный запрос — `400`.
- `GET /health` возвращает `200`, когда API видит обе таблицы в БД.

Проверить эффект того же задания непосредственно в PostgreSQL можно одним запросом.

```sh
docker compose exec -T db psql -U queue_admin -d queue -c "
  SELECT j.id, j.state, j.attempt, count(e.job_id) AS effects
  FROM jobs j LEFT JOIN effects e ON e.job_id = j.id
  WHERE j.request_key = 'experiment-17'
  GROUP BY j.id"
```

## Воспроизведение проверок

Интеграционные тесты используют настоящий PostgreSQL. Каждый тест создаёт собственную схему и удаляет её при завершении.

```sh
docker compose run --rm --build checks
```

При запуске непосредственно через `go test` интеграционные тесты требуют `TEST_DATABASE_URL` с `sslmode=verify-full`, доверенным сертификатом и правом создания тестовых схем. В Compose адрес читается из `TEST_DATABASE_URL_FILE`. При отсутствии переменной они помечаются как пропущенные.

Для запуска генератора нужен Go 1.25+ на машине с Docker CLI. Генератор сам создаёт Compose-проект, пустой том и случайный локальный порт. По завершении он удаляет этот стенд. Каждому запуску соответствует новый файл в `evidence/`. Ошибка проверки даёт ненулевой код выхода.

```sh
go run ./cmd/chaos -seed 7401
go run ./cmd/chaos -profile capacity -jobs 2000 -rps 100 -seed 8101
```

По умолчанию генератор отправляет 10 000 уникальных заданий, дублирует каждый третий POST и пытается отменить каждое пятое задание. Темп 100 запросов/с учитывает все три вида операций. Каждые две секунды он посылает SIGKILL случайному из восьми worker, проверяет код выхода 137 и запускает контейнер заново. После опустошения очереди генератор сверяет каждую строку с отправленным заданием и HTTP-квитанциями, проверяет таблицу эффектов, обходит страницы API и выборочно читает статус. Seed определяет параметры и выбор жертв. Порядок конкурентных транзакций зависит от планировщика.

Профиль `capacity` запускает штатные четыре worker и отправляет только новые задания. В логе видны число ещё ожидающих заданий после окончания входящего трафика и время, за которое они завершились.
